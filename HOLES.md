# Дыры и проблемы goose (форк ne-tort/goose)

Рабочий документ: известные дыры, подтверждённые причины (файл:строка, логи) и
предлагаемые решения. Обновляется по мере расследований. Дата последней ревизии:
2026-09-26.

---

## Дыра 1. После компакции ретраи ошибок провайдера отключаются до конца сессии

**Симптом.** Ошибка вида «Ran into this error: Server error (503 …)» появляется
в чате и ход завершается, хотя `GOOSE_PROVIDER_ERROR_RETRIES=-1`.

**Подтверждение.** Лог `20260926_170738.log`, сессия `20260926_53`:
14:01–14:02 ретраи работали (attempt 1–3/infinite); 15:33:49
`Performing message compaction`; 15:47:36 следующий 503 — surfaced **без**
«retrying provider error».

**Причина.** `ops_provider_error_retry.rs`: guard «kickoff not agent-visible →
not_applicable». После реактивной компакции kickoff становится невидимым
(содержимое влито в summary), guard срабатывает навсегда — все последующие
ошибки идут в `ExitOnErrorOperation` без ретрая. Guard добавлен как защита от
`reset_conversation` к невидимому kickoff (это уничтожило бы компакцию), но
блокирует и легитимные ретраи.

**Решение (предлагаемое).** Заменить семантику «reset к kickoff» на «unwind
последнего хода модели»: срезать с конца error/assistant-сообщения до
ближайшего user/tool-сообщения. После компакции откатывается только текущий ход
(компакция сохраняется), до компакции результат эквивалентен reset-у. Guard
убрать; счётчик попыток писать в operation-note anchor-сообщения. То же — для
empty-response ретрая в `goose-agent/src/inference.rs` (`reset_to_kickoff`).

**Статус:** подтверждено, фикс запланирован.

## Дыра 2. Тихий обрыв стрима принимается за готовый ответ

**Симптом.** Модель останавливается посреди предложения без ошибок («Порты яс»,
сессия `20260925_67`, сообщение сохранено 18:48:56 UTC; через 16 секунд — шторм
503 `model_not_found`: провайдер увёл модель посреди стрима).

**Причина.** `goose-provider-types/src/formats/openai.rs`,
`response_to_streaming_message`: парсер отслеживает `finish_reason` и
`[DONE]`, но если SSE-поток просто обрывается (соединение закрыто без ошибки и
без `[DONE]`), после цикла накопленный частичный текст отдаётся как обычное
сообщение. Legacy-цикл видит непустой текст → «нормальное завершение» → тихий
выход (`Ok(_) => exit_chat = true`).

**Решение (предлагаемое).** В конце стрима: если не было ни `[DONE]`, ни
`finish_reason` — возвращать
`ProviderError::NetworkError("stream ended without finish_reason")` вместо
тихого успеха. Обрыв пойдёт через обычные ретраи (NetworkError retriable) вместо
тихого принятия недописанного ответа. Частичный текст можно выдавать как
warning-нотификацию.

**Статус:** подтверждено, фикс запланирован.

## Дыра 3. Цикл на обрезанных tool call-ах («output token limit» на 176 символах)

**Симптом.** Повторяющиеся ошибки:
- `The tool call could not be parsed: -32602: The model's response was
  truncated — it hit the output token limit… Received 176 characters; cut off
  at: …docker run -d --name …`;
- следом `Tool 'unparseable_tool_call' is not available.`
- и по кругу: модель снова генерирует тот же вызов — снова обрезка.

**Причинная цепочка (проверено по коду):**
1. Модель генерирует tool call с длинным аргументом (docker-команда с
   переносами внутри JSON-строки). Стрим обрывается/режется.
2. `goose-provider-types/src/json.rs`: `parse_tool_arguments` →
   `looks_truncated()` (незакрытые скобки) → ошибка с текстом **«hit the output
   token limit»**. Важно: `looks_truncated` срабатывает по структуре JSON
   независимо от причины обрыва — при silent stream cut (дыра 2) причина
   указывается неверно.
   `repair_truncated_json` чинит только структурные закрыватели; обрыв внутри
   строкового литерала починить нельзя (и не должно — опасно исполнять
   частичную команду).
3. `agent.rs:3105-3125` (legacy) / `ops_toolcalling.rs` (SM): в историю пишется
   placeholder `Ok`-вызов с именем **`unparseable_tool_call`** и пустыми
   аргументами, а парный tool response несёт ошибку парсинга. Это сохраняет
   корректность истории для всех провайдерных форматтеров.
4. `ops_unknown_tool.rs:85-95`: на вызов `unparseable_tool_call` отвечает
   `Tool 'unparseable_tool_call' is not available` — второй симптом.
5. Модель получает ошибку, пробует снова — и снова генерирует тот же большой
   вызов. **Защиты от петли нет**: счётчика подряд идущих unparseable/truncated
   вызовов не существует, цикл может длиться сколько угодно (жжёт токены/деньги).

**Усугубляющий фактор — нечестный провайдер.** Запрошено
`max_tokens=128000`, обрезка произошла на ~176 символах аргументов — реальный
`finish_reason="length"` с таким крошечным выводом означает, что за именем
модели скрывается модель с куда меньшим лимитом вывода (либо провайдер режет
поток). По протоколу подмену не детектировать: провайдер эхом возвращает
запрошенное имя в `model` (проверено: в логах только `claude-opus-5.5`).

**Решение (предлагаемое, по убыванию эффекта):**
1. **Loop breaker**: счётчик подряд идущих truncated/unparseable tool call-ов
   за ход (operation-note, как `provider_retry_attempts`); после N (2–3) —
   прекратить кормить модель той же ошибкой, выдать пользователю ясное
   сообщение («провайдер режет вывод; смените модель/провайдера или уменьшите
   max_tokens») и завершить ход.
2. **Дизамбигуация причины** (связка с дырой 2): если стрим оборвался без
   `[DONE]`/`finish_reason` — в ошибке парсинга писать «stream interrupted»
   (retriable), а не «output token limit» (уводит модель в безнадёжный ретрай
   того же вызова).
3. **Текст-подсказка про подмену**: при `finish_reason="length"` с
   аномально малым выводом (usage.output_tokens ≪ max_tokens) дополнять ошибку
   строкой «the provider may be serving a smaller model than requested».
4. Проверить настройку `max_tokens` (GOOSE_MAX_TOKENS / модельная конфигурация):
   некоторые провайдеры плохо ведут себя с запрошенным 128k.

**Статус:** исследовано, фикс запланирован.

## Дыра 4. Лимит контекста для неизвестных моделей — fallback 128k; ошибки переполнения не распознаются

**Симптом.** Субагенты/чаты «останавливаются, когда много читают»; компакция не
срабатывает, хотя контекст фактически исчерпан.

**Причина.** Разрешение лимита (`context_limit.rs`): override
`GOOSE_CONTEXT_LIMIT` → `context_limit` из JSON кастомного провайдера →
канонический каталог → discovery → **fallback `DEFAULT_CONTEXT_LIMIT = 128_000`**
(`model.rs:11`). Для фейковых имён (cheapai) — всегда 128k. Компакция считает
токены по реальному usage (`session.usage.total_tokens`), но делит на
неправильный лимит: при реальном лимите, скажем, 32k переполнение происходит
задолго до порога 0.8×128k. Ошибки переполнения распознаются по 413/кодам и
английским фразам (`http_status.rs:136` — "context length", "context window"…);
русские/агрегаторские формулировки не распознаются → generic RequestFailed →
ретраи бессмысленного запроса вместо реактивной компакции.

**Решение:**
- Без кода (пользовательские настройки): задать `"context_limit"` в
  `custom_providers/custom_www.json` для каждой модели — **НЕ применяется по
  решению владельца** (лимиты в JSON не трогаем); или глобально
  `GOOSE_CONTEXT_LIMIT` в config.yaml; и `GOOSE_AUTO_COMPACT_THRESHOLD: 0.6`.
- Код: расширить `is_context_length_exceeded_message` маркерами агрегаторов
  (в т.ч. неанглийскими); опционально — адаптивное обучение: при ошибке,
  похожей на переполнение, запоминать наблюдаемый размер контекста как
  фактический лимит модели.

**Статус:** причина установлена; пользовательские настройки — на усмотрение
владельца; кодовый фикс запланирован.

## Дыра 5. Нечестный провайдер: подмена модели неотличима по протоколу

**Симптомы-отпечатки (все подтверждены логами cheapai.lol):**
- `503 model_not_found` посреди сессии (модель «увели»);
- premature `finish_reason="length"` с крошечным выводом (дыра 3);
- ошибки reasoning-контракта `reasoning_content must be passed back` от
  «claude» — типичный отпечаток DeepSeek-подобной модели за чужим именем.

**Ограничение.** Провайдер эхом возвращает запрошенное имя модели в ответе —
детект по полю `model` бесполезен. Полного клиентского решения нет.

**Смягчение:** поведенческие эвристики (дыры 3–4) + честные сообщения
пользователю + loop breaker против циклов на «кривой» модели.

**Статус:** задокументировано; клиентское решение принципиально частичное.
